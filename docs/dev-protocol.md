# 开发分工协议 · 架构师出单 / 执行工程师开发 / 架构师验收

> 适用：veritas 仓库全部非平凡改动。目的：两个工具之间**不靠聊天记忆协作**——
> 一切以进了 git 的本文件、`docs/HANDOFF.md` 工单与 `docs/architecture-map-2026-10-12.html` 为准。
> 与本文件冲突的历史写法，以本文件为准。

## 1. 角色与边界

| 角色 | 工具 | 负责 | 明确不做 |
|---|---|---|---|
| **架构师／规划** | Qoder | 读代码与产物定位问题、出工单（含开箱可跑的验收判据）、**出单即附可粘贴的开工提示词（§9.1）**、**独立复放验收**、review diff、同步图与交接页、提 commit | 不写生产代码（用户另行指定除外）；不采信执行工程师的自述当结论 |
| **执行工程师** | Cursor | 按工单实现、补测试、**开工前先做 §3.0 前提核查**、按 §3 处理开发中发现的问题、**工单策略／判据本身错了按 §3.4 质疑**、回写状态行与「动了哪些文件」 | 不自派工单、不改写工单要求、不把状态写成「已验收」；**也不许明知单写错了还照着做完好交差** |
| **拍板人** | 用户 | 定优先级与口径、决定哪些单可以不等官方材料先动、对 §3.2 类改动做go/no-go | — |

## 2. 工单格式（`docs/HANDOFF.md` §5，每单固定六段）

1. **现状**：带实测复现（探针命令＋真实输出）与 `文件:行号`；禁止只写"可能有问题"。
2. **要求**：编号列出，每条可单独验证；需要多处落点的（返回值／`ingest_notes`＋`triage`／界面／报告）逐点写死。
3. **明确禁止**：不许顺手做的东西写在这里（改判定、改统计口径、放宽封顶、加 LLM、动 `cases/`）。
4. **要求补的测试**：a/b/c… 逐条，含至少一条**反向断言**（只改文案不改条件要能被抓到）。
5. **验收判据（架构师独立复放）**：命令级，见 §5 写法约束。
6. **状态行**：`状态｜验收` 两格，见 §4 状态机。

派工单另有**第七段「开工提示词」**（§9.1 要求，与工单同一笔 commit 存盘）；它是下达边界的话术，不替代前六段——
六段才是验收依据，两者口径冲突时**以六段为准并当场修提示词**。

## 3. 开发中发现问题的处理路径（本条为协议核心，勿绕过）

**0. 开工前置核查（先验前提，再动工；2026-10-16 加）**：读完单不许立刻写代码，先花一次最小复现核三条——
① 单里引用的 `文件:行号` 还在不在、说的是不是那件事；② 要求指的位置是不是**真正产生该现象的位置**
（改这里，症状会不会真的消失）；③ 按单做完之后，验收判据承诺的那行输出会不会真的出现。
三条有一条对不上，按下面第 4 条走，**不要"照着错的做完好交差"**——照错执行到底不是执行力，是把我写错的口径钉进代码。

1. **属本单范围内的实现问题** → 就地修，回写时列「偏离工单之处＋原因」。
2. **会改结论的改动**（判定逻辑、统计口径、提示词纪律、置信度分量）→ **停手**，把发现连同实测写成
   新工单条目提案交架构师，由用户拍 go/no-go；**当前单不得顺手做**。判据：
   「改完同样的输入，`report.json` 里某个已有字段会不会变值？」会变 = 属本条。
3. **顺带发现的新洞** → 不修；回写里加一段「发现（未修）」，架构师负责立项编号与排期。
4. **工单本身的策略／口径／判据错了**（不是实现做不到，是**这么做不对**）→ 执行工程师**有权也有义务质疑**，
   且质疑是义务不是冒犯。回写里加一段「**工单质疑**」，每条三行：
   `错在哪（引用工单原句）｜实测证据（命令＋真实输出）｜建议改成（一句话）`。
   - 质疑成立且**不改结论**（落点、函数、字段名、判据数字写错）→ 我当场改单，它按改后的单继续；
   - 质疑成立且**会改结论**（第 2 条判据）→ 当前单**冻结该点**，其余照做，等用户拍板；
   - 质疑不成立 → 我必须在原单写明**驳回理由＋证据**，不许沉默略过。驳回后它按原单做完，
     不得重复提同一条刷屏。
   - **反滥用**：只有带实测证据的才算质疑；"我觉得这样更优雅""这个功能应该顺便做全"不算，
     属第 1／3 条。单纯工作量大的异议也不算质疑，那叫排期问题，直接说。
   - 对称义务：**架构师的行号和判据错一次就要留痕一次**。历史上我先把遍历上限的行号写成 `case_loader.py:345`
     （真值 `:352`／`:370`）、又把 C-9 写成"唯一一道不披露的口"（台账那条本就例外）——
     这类错误只有执行方在第一线撞见，所以这条通道必须开着。

## 4. 状态机

```
待开工 → 开发中 → 已改完（YYYY-MM-DD），待架构师验收 → 已验收通过（YYYY-MM-DD 独立复放） → 已提交
```

「已验收通过」这一格**只由架构师填写**，内容必须是复放记录（跑什么、看到什么、几条尾巴），
不接受"看起来没问题"。验收中发现不达标 → 状态退回「开发中」并在原单追加复放失败证据。

带「工单质疑」的单停在「已改完」前一格不算迟到：质疑**必须在同一轮里得到答复**（改单，或写明驳回理由＋证据），
架构师不回话就是失职，不许让它挂着到答辩前一天。

## 5. 验收判据写法（约束架构师自己）

- **开箱可跑**：命令＋期望输出；仓库当前**没有** `scripts/score_artifacts.py` 的基线 JSON，
  判据不得引用 `--check` 这类需要基线的入口。
- **至少一条反向断言**：防只改文案不改条件。
- **至少一条零回归**：`git diff --stat cases/` 为空，或存量产物字段计数不变。
- **不采信自述**：测试数、产物数、封顶行为必须由架构师自己跑一遍探针复现。
- **凡引用官方口径，必须逐条带 `rubric:行号` 出处**（2026-10-17 C-12 第四轮的教训）。
  我给执行方的权重规则（precision 按提交条数加权）是我自己推的，没引官方 `rubric:225`
  「先逐条结论计算，再按**标准答案规模**加权汇总」——那版实现因此偏离官方，且偏离方向是**读数偏高**。
  执行方无从质疑一句没有出处的指令。规则：**口径类指令要么带原文行号，要么明写「官方未规定，此处为自选口径＋理由」**；
  同一指标在不同条目里口径可能不同（2.4 按金标规模加权、2.5 是全局集合比值），**"统一起来更好看"不是理由**。
- **改「共享权重／分母／聚合」这类机制，判据必须含混合格与反例格**：
  只看两个极端（全对提交／全空提交）会同时漏掉「金标为空×提交非空」与「金标非空×提交空」这两格。
  判据里把**四象限逐格**的数值形状列全，谁缺格谁没过。
- **判据里每个期望值，出单前必须先在"改动前"的代码上跑一遍**（2026-10-17 C-12 第五轮的教训，我的错）：
  跑出来**与期望相同**＝这条判据是空的（改动前就满足，抓不住任何东西）；跑不出来才算数。
  我上一版把 `Precision_sup=0.4` 写成判据，却没量过改动前是多少——实际改动前是 `1.0`，而那个 `0.4` **在这轮没被授权的改动范围里数学上取不到**
  （它需要遍历方向也从"按提交行"改成"按金标行"，我那时把那一件分给了下一张单）。
  规则：**跨单的机制不要拆开**——先跑一遍判据、看它需要哪几处一起改，把前置并进同一轮；
  并用一条「已验收读数必须逐字不变」的判据兜住合并带来的副作用（本轮＝上帝提交 `7/6/6/7/6`、白卷 `0/0/0/0/0`）。
- **本轮改写凡是"把列表压成按 key 索引"，收口复放就必须造"同一 key 出现两次＋换序"的用例**（2026-10-17 C-12 第五轮的教训，**通过收口那一轮抓到的洞是那一轮自己引入的**）：
  第五轮把评分器改成按金标遍历，顺带用 `{row["question_id"]: row for row in conclusions}` 建索引——
  字典推导对重复 key 是**后写覆盖前写**，被覆盖那行静默消失。同一份材料只换两行先后，实测 2.4 的两项从 `4／6` 跳到 `0／0`，
  而且偏的一侧正是乐观侧（把本轮刚验收的 2.4.1 一票否决吃掉）。**"判据全过＋回归全绿"证不出这一点**，因为六案金标 key 无重复。
  规则：改动的结构里出现 **dict 推导／`group by` key／"最后一行赢"** 时，验收清单固定加两格——
  ① 同一 key 两行、换序后五项读数**逐字相同**；② 该 key 只有一行时**不出现**为合并而写的披露行（反例，防空转）。
  合并类改动还要写明**判定发生在合并之前还是之后**：本例的"裸结论"判定若在合并后做，一票否决就被合并吃了。

## 6. 仓库三道纪律（每次改动默认适用）

1. **零 LLM 优先**：能用确定性代码／机械闸解决的，不加模型调用；新闸与 skill 成对出现（没闸的 skill 是许愿）。
2. **丢件必须可见**：任何 `return`／`continue`／截断造成的材料丢弃，都要有披露出口；
   **披露≠召回**，写口径时两句都要在。
3. **测试期禁真调用**：新测试必须打桩；`tests/conftest.py` 有守卫，忘打桩当场炸。key 不进仓库、不进 U 盘明文。

## 7. 提交规矩（架构师执行）

- **一工单一 commit**（代码＋测试），标题带单号：`fix(scope): …（工单 C-x）`。
- **文档另起一笔**：`docs(交接+方案): …`，同一笔里同步 HANDOFF 状态行与本文件提到的图。
- commit message 讲「为什么」并带实测数字；**不 push、不 `--no-verify`、不 amend 已提交内容**。
- `CLAUDE.md` 是指向 `AGENTS.md` 的符号链接（同一份内容），改 `AGENTS.md` 即同步，不必也不许复制出第二份。

## 8. 图与文档同步（方案总览的口径纪律）

`docs/architecture-map-2026-10-12.html` ＝总体架构图＋核心技术主张＋关键指标承诺。规则：

- **每个格子必须回指代码行号或产物字段**，文档口径的绿不算绿；写行号前用 `sed -n 'Np' 文件` 逐行核过。
- 代码改完**当天**同步图；旧口径（被代码推翻的说法）必须清零，不许并存。
- 指标承诺表里每个数字都要能给出复放命令；未量化的写「［未量］」，不许估。

## 9. 开工指令模板（用户粘贴给 Cursor）

**§9.0 通用模板**（单号填进去即可用）：

```
读 docs/dev-protocol.md（分工协议）和 docs/HANDOFF.md §5 的工单 C-<n>，你是执行工程师。
先做协议 §3.0 前提核查（行号还在不在／要求指的位置是不是真因／照做完判据会不会真出现），核完再动工。
按工单六段实现，只动「要求」列出的落点；「明确禁止」一条不许碰。
开发中若发现问题，按协议 §3 处理：本单内的就地修并写「偏离工单之处」，
会改结论的停手写提案，新发现的洞只记「发现（未修）」不要顺手修。
如果你判定这张单的策略／口径／验收判据本身是错的，按 §3.4 写「工单质疑」：
错在哪（引原句）＋实测证据（命令与真实输出）＋建议改成什么。质疑是义务，不是冒犯；
但"我觉得更优雅""顺便做全"不算质疑。也不要明知单写错了还照着做完好交差。
完成后：pytest tests -q 全绿、git diff --stat cases/ 为空，
回写工单状态行为「已改完（今天日期），待架构师验收」＋动了哪些文件＋新增用例名＋pytest 尾行。
不要提交，不要 push，验收归 Qoder。
```

**§9.1 出单即附提示词（架构师义务，2026-10-16 加）**：只要有新单或单子改口径，架构师**必须同一条回复里**
给出可直接粘贴给 Cursor 的开工提示词，不等用户开口要。写法规则：

1. **一单一贴**：不合并成"这两张单一起做"。有依赖或会撞同一文件（例：多单都改 `app/config.py`）时，
   明确写出**先后顺序**与撞车点。
2. 提示词必须含**六样**：**单号**、**允许动的落点**、**禁止项**、**前提核查＋质疑通道（§3.0／§3.4）**、
   **完成后回写什么**、**不提交不 push**。
3. **不许把工单正文抄进提示词当唯一信息源**——只给"读哪儿＋做什么＋边界"，实现细节以 `docs/HANDOFF.md` §5 原文为准。
   两处并存必然漂移，漂移就是工单口径被悄悄改写。
4. 贴出的提示词与工单**同一笔 commit 存盘**（写在工单的「开工提示词」小段里），
   换工具时接手方能看见当时下达的确切边界，而不是转述。

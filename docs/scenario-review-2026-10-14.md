# 场景重判与设计结论（2026-10-14 下午，七条）

背景：官方宣讲会材料到手前，用户提出「我们可能把场景判断错了」。随后六轮共创收敛出下面七条。
**这批结论是设计判断，不是待办**；官方验收标准与评分细则到手后，才允许往每条上贴分值、排工期。

每条末尾标注可信度：**[实测]** ＝ 有代码或产物数据支撑（可复放）；**[推演]** ＝ 结构上成立但未验证。

## 1. 场景重判：甲方是「舆情流式研判」，我们按「静态一次性案卷」设计 [实测]

真实场景特征：事件随时间演进、日均几十万条、100 条里 90 条是抄的且滞后、主体立场导致瞒报与口径不一致
（原话见 `docs/contest-briefing-2026-10-14.md` §4）。

我们的现状：一个 case ＝ 一句 `question` + 一批一次性摄取的 sources → 跑一遍 → 出报告。
三个演示案例中只有 `rumor-vs-official` 勉强对得上，且那是 2026-10-12 才补的。

连带发现：官方评测是「给原始数据 + **问题清单**，逐题交证据与结论」，而
`Dossier.question` 是单个字符串（`app/core/evidence.py:258`），全仓库无 `questions` 复数概念
——**报告形态 vs 答题纸形态**的错配。是否要改，取决于样例集实际字段结构（未到手）。

## 2. 「独立信源簇」是系统里缺失的一等公民 [实测]

一条真信源被 90 家转载，按现行覆盖分量公式：coverage **0.500 → 1.000**，即**置信度整体虚高 100%**
（用 `app/core/confidence.py` 现行公式算得，可复放）。`near_dup`（`app/core/dup_check.py`）只亮黄牌，
不进计数、不进分量。

簇要成为数据结构（信源上挂：所属簇 / 第几代 / 事件时点），四个出口都踩在它上面：

1. 覆盖分量按**独立簇数**计条数（治虚高）；
2. **跨簇**同代数字不同 ＝ 真冲突，进消解队列；
3. **簇内**数字不同 ＝ 稿件被改过（改数、删限定语、加评论）→ 篡改/加工检测，谣言监测的正靶心；
4. **孤证显影**：「12 条证据 · 来自 1 个独立信源」，而不是给「数据数量与一致性」打高分。

报告里那行证据说明若显示「来自 3 个独立信源 · 含 2 代更新 · 最早出处：新华社 09-25 14:02」，
是答辩最能打的画面——直接证明我们知道哪些是抄的。

## 3. 时间不是归拢的钥匙，是定向的钥匙 [推演]

内容相似先聚簇，时间用来定「谁是源头、谁是下游」与分代。规则：**同簇跨代数字变化＝演变；
跨簇同一时点数字不同＝冲突**。这一条直接治掉 `fact_ledger.find_collisions()` 现在
「按（实体,指标）分组、差 >1% 就算对撞、**完全不看 date**」的毛病——
`Fact.date` 字段已存在但只用于展示（`app/core/fact_ledger.py:56,113`）。
更糟的是台账会注入分析师提示词「以下资料冲突必须在结论中回应」，等于**我们制造假冲突并逼模型解释它**。

三个坑：① 发布时间 ≠ 事件时点（旧闻新炒；我们只有 `published_at`，缺 as-of）；
② 时间精度不足时不许硬判方向，标「无从判定」（复用 2026-10-13 立的三态规矩）；
③ 忠实转载权威通报不该扣分——簇是**去重计数**，不是惩罚转载，否则从虚高翻成虚低。

## 4. 「像人一样研判」的十格对照表：四格空白全被甲方点过名 [实测]

| 人读一条新闻时在做的事 | 系统承接情况 |
|---|---|
| 1 这是谁说的、他凭什么知道 | 弱：`source_type` + credibility 标量，无「一手观察/听人说/推测」之分 |
| 2 跟我已知的比哪部分是新的 | 弱：`dossier_diff` 能对照两次产物，但案卷静态、无「已知状态」 |
| 3 拆事实：时间/主体/数量/因果 | **有**：`fact_ledger` 抽（实体×指标×数值×信源） |
| 4 别人怎么说、口径一样吗 | **无**：只比数值差 >1%，不看统计范围 |
| 5 这条是重复、更新还是矛盾 | 弱：`near_dup` 只亮黄牌，不进计数不进分 |
| 6 先发和后发该信哪个 | 弱：`as_of`/`stale` 闸在，但台账判定不用日期 |
| 7 他这么说是不是想要什么 | **无**：立场偏差完全没建模 |
| 8 我该用多重的语气 | **有**：`hedge` + `level_tone` 两道闸 |
| 9 什么证据出现我会改判断 | **无**：只有 redteam 人设写了「以证伪为立场」 |
| 10 要不要报、多急、报给谁 | **无**：主席只「正面回答议题」，无行动层 |

附带抓到一条：`EvidenceLevel.A` 的定义写着「同行评审 / 一手数据 / **多源一致**」
（`app/core/evidence.py:50`）——在舆情场景里多源一致很可能就是转载堆量，
**最高证据等级把要防的坑写成了加分条件**。

规矩：树的每枝终点必须落到**字段 / 闸 / 分量**，落不到的不是「没做」而是「做不到」，
要老实写进「已知边界」。颗粒度硬边界＝能回答「官方扣分能不能落到这个环节」为止。

## 5. 打分公式：先过否决闸，再组内加权，组间相乘 [推演]

用户设想：10 维各有权重，每个智能体对 10 维打分，加权求和得该智能体置信度，三智能体后主控汇总。
评估结论：方向可行（且官方明说不限成本，解锁了 token 开销），但三处必须改：

1. **纯加权和会丢掉一票否决**——引文不命中、数字无出处、答非所问不能被其他九项救回来。
   现行四分量是**相乘**的，天生不互补，这是它唯一的优点，别丢。
2. **10 维里约 6 维可机械判定，绝不该交给模型自评**（让被告自己量刑：谄媚、过自信、同料两次跑分不同）。
   模型只判立场/可证伪/紧迫度，且用**高·中·低三档 + 必须指出依据段落**，不给 0–1 连续值。
3. **主控不许平均三 agent 总分**（＝甲方点名的「简单投票」）。要**逐维比分歧**：
   同一维度三人打出 0.8/0.3/0.6，分歧本身就是「这一维不可信」的信号，
   可顶替现行粗粒度的「署名数 ÷ 编队人数」一致分量。这才是多智能体真正独有的产出。

## 6. 权重反推：现有样本零方差，反推不出来 [实测]

用户设想：知道问题和答案，倒推那 10 维权重。死结是**零方差特征不可识别**：
现有私有 gold 是 `eval/questions.jsonl` 30 条（带 `ground_seg` + `value`，7 家公司），
全是窄题数值查找——无转载、无滞后、无立场，**那几维取值恒定**，给什么权重都不改变预测。
检索层实测 30/30 全中（`eval/recall_real_report.md`），也无方差可用。
模型层只有 5 题历史结果（M1 5/5、M2 4/5，2026-10-10）。

出路：① 先造带那三维的样本，最省钱的来源是**事后真相回填**（输入＝当时可见报道，
答案＝后来证实/证伪的结论，免费可批量）；② 拟合目标用**规则树/否决顺序**（几十条够），
不是权重（10 特征经验上需 200–300 条）；③ 权重本身先不反推，改做**敏感性检验**
（±30% 扰动看结论排序变不变；排序不变则精确权重不重要——这本身就是能拿去答辩的答案）。

## 7. 收敛性判据要按问题类型分岔 [推演]

用户设想：同一事件各信源得出的结论差距不该太大。
**事实型问题成立**（伤亡数、时间、地点、是否发生——存在真值，各条信息是带噪读数）；
**评价型问题不成立**（救援是否有力、风险大不大——分歧是资产不是噪声）。
硬把收敛套到评价型，等于亲手抹掉甲方专门要的「多视角」。
判据：事实型看收敛度，评价型看分歧是否被解释清楚。

工程顺序提醒：**先聚簇再研判**，不是先研判再去重——逐条研判时模型看不见「这两条是同一篇」，
会把转载当印证写进结论。成本上 100 条 → 3 簇是 33 倍差距，但顺序错了**语义就错了**，
这才是主要理由。

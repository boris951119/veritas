# 开发分工协议 · 架构师出单 / 执行工程师开发 / 架构师验收

> 适用：veritas 仓库全部非平凡改动。目的：两个工具之间**不靠聊天记忆协作**——
> 一切以进了 git 的本文件、`docs/HANDOFF.md` 工单与 `docs/architecture-map-2026-10-12.html` 为准。
> 与本文件冲突的历史写法，以本文件为准。

## 1. 角色与边界

| 角色 | 工具 | 负责 | 明确不做 |
|---|---|---|---|
| **架构师／规划** | Qoder | 读代码与产物定位问题、出工单（含开箱可跑的验收判据）、**出单即附可粘贴的开工提示词（§9.1）**、**独立复放验收**、review diff、同步图与交接页、提 commit | 不写生产代码（用户另行指定除外）；不采信执行工程师的自述当结论 |
| **执行工程师** | Cursor | 按工单实现、补测试、**开工前先做 §3.0 前提核查**、按 §3 处理开发中发现的问题、**工单策略／判据本身错了按 §3.4 质疑**、回写状态行与「动了哪些文件」 | 不自派工单、不改写工单要求、不把状态写成「已验收」；**也不许明知单写错了还照着做完好交差** |
| **拍板人** | 用户 | 定优先级与口径、决定哪些单可以不等官方材料先动、对 §3.2 类改动做go/no-go | — |

## 2. 工单格式（`docs/HANDOFF.md` §5，每单固定六段）

1. **现状**：带实测复现（探针命令＋真实输出）与 `文件:行号`；禁止只写"可能有问题"。
2. **要求**：编号列出，每条可单独验证；需要多处落点的（返回值／`ingest_notes`＋`triage`／界面／报告）逐点写死。
3. **明确禁止**：不许顺手做的东西写在这里（改判定、改统计口径、放宽封顶、加 LLM、动 `cases/`）。
4. **要求补的测试**：a/b/c… 逐条，含至少一条**反向断言**（只改文案不改条件要能被抓到）。
5. **验收判据（架构师独立复放）**：命令级，见 §5 写法约束。
6. **状态行**：`状态｜验收` 两格，见 §4 状态机。

派工单另有**第七段「开工提示词」**（§9.1 要求，与工单同一笔 commit 存盘）；它是下达边界的话术，不替代前六段——
六段才是验收依据，两者口径冲突时**以六段为准并当场修提示词**。

## 3. 开发中发现问题的处理路径（本条为协议核心，勿绕过）

**0. 开工前置核查（先验前提，再动工；2026-10-16 加）**：读完单不许立刻写代码，先花一次最小复现核三条——
① 单里引用的 `文件:行号` 还在不在、说的是不是那件事；② 要求指的位置是不是**真正产生该现象的位置**
（改这里，症状会不会真的消失）；③ 按单做完之后，验收判据承诺的那行输出会不会真的出现。
三条有一条对不上，按下面第 4 条走，**不要"照着错的做完好交差"**——照错执行到底不是执行力，是把我写错的口径钉进代码。

1. **属本单范围内的实现问题** → 就地修，回写时列「偏离工单之处＋原因」。
2. **会改结论的改动**（判定逻辑、统计口径、提示词纪律、置信度分量）→ **停手**，把发现连同实测写成
   新工单条目提案交架构师，由用户拍 go/no-go；**当前单不得顺手做**。判据：
   「改完同样的输入，`report.json` 里某个已有字段会不会变值？」会变 = 属本条。
3. **顺带发现的新洞** → 不修；回写里加一段「发现（未修）」，架构师负责立项编号与排期。
4. **工单本身的策略／口径／判据错了**（不是实现做不到，是**这么做不对**）→ 执行工程师**有权也有义务质疑**，
   且质疑是义务不是冒犯。回写里加一段「**工单质疑**」，每条三行：
   `错在哪（引用工单原句）｜实测证据（命令＋真实输出）｜建议改成（一句话）`。
   - 质疑成立且**不改结论**（落点、函数、字段名、判据数字写错）→ 我当场改单，它按改后的单继续；
   - 质疑成立且**会改结论**（第 2 条判据）→ 当前单**冻结该点**，其余照做，等用户拍板；
   - 质疑不成立 → 我必须在原单写明**驳回理由＋证据**，不许沉默略过。驳回后它按原单做完，
     不得重复提同一条刷屏。
   - **反滥用**：只有带实测证据的才算质疑；"我觉得这样更优雅""这个功能应该顺便做全"不算，
     属第 1／3 条。单纯工作量大的异议也不算质疑，那叫排期问题，直接说。
   - 对称义务：**架构师的行号和判据错一次就要留痕一次**。历史上我先把遍历上限的行号写成 `case_loader.py:345`
     （真值 `:352`／`:370`）、又把 C-9 写成"唯一一道不披露的口"（台账那条本就例外）——
     这类错误只有执行方在第一线撞见，所以这条通道必须开着。

## 4. 状态机

```
待开工 → 开发中 → 已改完（YYYY-MM-DD），待架构师验收 → 已验收通过（YYYY-MM-DD 独立复放） → 已提交
```

「已验收通过」这一格**只由架构师填写**，内容必须是复放记录（跑什么、看到什么、几条尾巴），
不接受"看起来没问题"。验收中发现不达标 → 状态退回「开发中」并在原单追加复放失败证据。

带「工单质疑」的单停在「已改完」前一格不算迟到：质疑**必须在同一轮里得到答复**（改单，或写明驳回理由＋证据），
架构师不回话就是失职，不许让它挂着到答辩前一天。

## 5. 验收判据写法（约束架构师自己）

- **开箱可跑**：命令＋期望输出；仓库当前**没有** `scripts/score_artifacts.py` 的基线 JSON，
  判据不得引用 `--check` 这类需要基线的入口。
- **至少一条反向断言**：防只改文案不改条件。
- **至少一条零回归**：`git diff --stat cases/` 为空，或存量产物字段计数不变。
- **不采信自述**：测试数、产物数、封顶行为必须由架构师自己跑一遍探针复现。
- **凡引用官方口径，必须逐条带 `rubric:行号` 出处**（2026-10-17 C-12 第四轮的教训）。
  我给执行方的权重规则（precision 按提交条数加权）是我自己推的，没引官方 `rubric:225`
  「先逐条结论计算，再按**标准答案规模**加权汇总」——那版实现因此偏离官方，且偏离方向是**读数偏高**。
  执行方无从质疑一句没有出处的指令。规则：**口径类指令要么带原文行号，要么明写「官方未规定，此处为自选口径＋理由」**；
  同一指标在不同条目里口径可能不同（2.4 按金标规模加权、2.5 是全局集合比值），**"统一起来更好看"不是理由**。
- **改「共享权重／分母／聚合」这类机制，判据必须含混合格与反例格**：
  只看两个极端（全对提交／全空提交）会同时漏掉「金标为空×提交非空」与「金标非空×提交空」这两格。
  判据里把**四象限逐格**的数值形状列全，谁缺格谁没过。
- **判据里每个期望值，出单前必须先在"改动前"的代码上跑一遍**（2026-10-17 C-12 第五轮的教训，我的错）：
  跑出来**与期望相同**＝这条判据是空的（改动前就满足，抓不住任何东西）；跑不出来才算数。
  我上一版把 `Precision_sup=0.4` 写成判据，却没量过改动前是多少——实际改动前是 `1.0`，而那个 `0.4` **在这轮没被授权的改动范围里数学上取不到**
  （它需要遍历方向也从"按提交行"改成"按金标行"，我那时把那一件分给了下一张单）。
  规则：**跨单的机制不要拆开**——先跑一遍判据、看它需要哪几处一起改，把前置并进同一轮；
  并用一条「已验收读数必须逐字不变」的判据兜住合并带来的副作用（本轮＝上帝提交 `7/6/6/7/6`、白卷 `0/0/0/0/0`）。
- **「grep 命中数」这类结构判据有两个坑，都得用"改前基线数"堵**（2026-10-18 C-16b，同日踩两次，都是我的错）：
  ① **计数恰好改前就成立＝空判据**——我写「`grep 字面量 app/` 恰一处」当"只有一处实现"的证据，实测改前就已恰一处（那处正是待重构的内联 dict），执行方什么都不做也跑绿。
  ⇒ 结构类判据一律写成**「改前 N 处 ⇒ 改后 1 处」的减法**，把改前计数写进单里；并且**读方（消费该字段的代码）要显式排除**，否则永远红。
  ② **模式里的 `*` 不加 `-F` 就当正则量词**——我第二版写 `grep -rn 'glob("\*/out\*'`，本意找字面 `"*/out*"`，实测**改前 0 命中**＝又是一条空判据。
  ⇒ 判据里的 grep **模式含 `*`／`(`／`[`／`.` 一律 `-F`**（或 `-E` 加正确转义），并在单里注明"用的是 `-F`"。
  两条合成一句可执行纪律：**每条 grep 判据必须自带"改前跑这条命令的输出"，贴出命中数；改前后同一个数，就把这条判据删掉或改写，别留给验收。**
- **本轮改写凡是"把列表压成按 key 索引"，收口复放就必须造"同一 key 出现两次＋换序"的用例**（2026-10-17 C-12 第五轮的教训，**通过收口那一轮抓到的洞是那一轮自己引入的**）：
  第五轮把评分器改成按金标遍历，顺带用 `{row["question_id"]: row for row in conclusions}` 建索引——
  字典推导对重复 key 是**后写覆盖前写**，被覆盖那行静默消失。同一份材料只换两行先后，实测 2.4 的两项从 `4／6` 跳到 `0／0`，
  而且偏的一侧正是乐观侧（把本轮刚验收的 2.4.1 一票否决吃掉）。**"判据全过＋回归全绿"证不出这一点**，因为六案金标 key 无重复。
  规则：改动的结构里出现 **dict 推导／`group by` key／"最后一行赢"** 时，验收清单固定加两格——
  ① 同一 key 两行、换序后五项读数**逐字相同**；② 该 key 只有一行时**不出现**为合并而写的披露行（反例，防空转）。
  合并类改动还要写明**判定发生在合并之前还是之后**：本例的"裸结论"判定若在合并后做，一票否决就被合并吃了。
- **「压成按 key 索引／取并集」这类指令，出单前必须先量**金标自己有没有重复 key**（2026-10-17 C-15 的教训，我的错）：
  我给 C-15 第 ⑤ 件写的是「支撑侧与冲突侧都按 `(doc_id, para_id)` 取并集」——没查金标。实测金标里同一 `(doc, para)`
  被一题引多次（六案共 5 处：吉隆 2、印航 1、柬泰 2），而 `exact_hits` 是**一对一消耗**的多重集语义 ⇒
  并集把 3 次压成 1 次，`score_2_5_1` 从 **7 掉到 0**。执行方自己发现并偏离了我的指令（单行不做并集），才保住已验收的上帝提交读数。
  规则：**两侧口径不要笼统写"同法"**；涉及去重／并集／`set()` 的指令，出单前先跑一遍"金标重复 key 清单"，
  并写明**评分侧是集合语义还是多重集语义**（本项目＝多重集，所以"合并"必然是损失性的）。
- **动因里凡是"丢 X 分换 Y 分，所以净赚"的算术，必须逐格跑一遍档位分布**（2026-10-17 C-15 收口复放推翻了我这条，教训比实现重要）：
  我写「N=3 时丢一题最多 −5.00＜−6 ⇒ 宁可不交净赚 1.0～6.0 分」，这个 6 是**最有利档**（`Recall_sup ≥ 0.85` 那一档），不是通例。
  按六案真金标逐题算：丢完仍在 +6 档的**一题都没有**（单题金标段数占本案 12%～44%，删任一题都跌破 0.85），
  实际档位分布 4／2／0 各 7／8／3 题 ⇒ 只要裸结论内容判对，丢题 **18/18 全亏 −1.0～−5.0**。
  规则：**"换分"类算术要写成表格（每档赚回多少 × 真金标落在该档的题数）**，跑一遍再发单；
  算不平就在单里写"这是口径/价值判断，不是算出来的最优"，别让执行方以为自己在实现一个已证的收益。

- **凡新增「从 A 推 B」的映射，判据必须把 A 与它可能相关的**另一个维度**排成笛卡尔积逐格给期望值**（2026-10-17 C-14 的教训，我的错）：
  我把 `resolution_type` 定义成「由 `method` 机械映射」，可消解记录里**还有 `decision_path` 这个维度**；
  四格里我只写中了对角线上的三格（`evidence_weight`→语义可信度、`source_majority`→多数投票、`tie`→其他），
  漏了「`method=arbitration` × `path=strength`」＝**模型本来就选对强侧**那一格——它在真实运行里是常态，落「其他」后
  同一份 `basis` 的 `type_applies` 又写「按证据强度裁决」，两句自相矛盾，正好打在 3.3 的「依据可核 3 分」上。
  规则：给映射表时先问「这个值除了 A 还由不由第二个维度决定？」；执行方把漏格**当期望值钉进了用例**（`test_g:190-196`），
  说明**判据没覆盖的格子会被测试固化成"故意的"**，之后更难发现。
- **工单里凡「唯一的 X 构造点／唯一的调用点／只有一处」这类前提，出单时必须附仓库级 grep 命令原文，执行方 §3.0 核查也要附输出行**（2026-10-17 C-14 的教训，也是我的错）：
  我写了「`arbiter.py:376-382` 是唯一的 `Resolution` 构造点」，执行方回写「`arbiter.py:376-382` 仍是唯一 `Resolution(`」——
  这句**照抄了我的断言、不是核查过的事实**；`grep -rn "Resolution(" app/` 一行就会撞见 `app/core/human_ops.py:62`（工作台「人工改判」），
  那条路径不走机械闸，新字段全是空值，而空 `dict` 又恰好躲过导出层 `basis in (None,"")` 的缺失上报。规则：**"唯一"是需证明的命题，不是背景描述**。
- **新增「每次调用都重算集合级 O(n²) 闸」的机制，判据固定加一条计时格或调用次数格**（C-14 R-C14-3）：
  `_source_fold` 每条冲突把 `near_dup_pairs` 算 4 遍，我出单前只量了**同源污染率（4.5%）**没量过**重算次数**——
  真数出来是官方最大案（137 信源）**1365 ms/冲突**、10 条冲突 ≈13.7 s 纯重算。
  判据写法用 **monkeypatch 数调用次数**（比计时稳定，CI 上不会因机器抖动而假红）＋一条「取值逐字不变」兜住语义。
- **「A 枪毙了 B」这类因果归属，出单前必须按个体 id 反查留痕；「发生率」必须注明是哪一级的率**（2026-10-17 C-16 的教训，我的错）：
  我把「零采纳」归因给引文闸、并据此建议用户选③，实测只撑住一半——34 份留档 run 上**结论级 10/304＝3.3%、题级 0/34**（＝那道闸从未触发过的那一格），
  而 10 条里 **5 条压根没经过闸**（`app/agents/base.py:160-161` 引用段落不存在时静默 `continue`，随后仍被标「资料不足」，台账零留痕——这是 §6 纪律 2「丢件必须可见」被自家代码破掉的一格）。
  两个率差一个数量级，**拿错那一级就会开出错方向的单**（差点对方的修法是"放宽引文闸阈值"，而那 5 条根本不过闸）。
  规则：**归因要按 id 逐条回查证据链，聚合数要注明层级（结论级／题级／全库级）**——同一现象的不同率不能互换使用。

- **工单点名「X 文件里那道洞」时，出单方必须先做全仓同形 grep 并把命中原文写进单里**（2026-10-17 C-16 验收的新防线，还是我的错，与上面「唯一构造点」是同一条纪律的反面）：
  我写「`base.py:160-161` 那道段落不存在就静默 `continue`」，执行方照单只修了 `base.py`；验收时我 `grep -rn "dossier.segment(" app/` 一看，**同形条件有三处**——`repair.py:156`（修复环，noncompliant 档真模型必走）与 `ingress.py:61`（MCP 第三方入卷）一个字没动。
  「同一处代码只在一个文件里出现」同样是需证明的命题。**修法层面还给出第二条**：一类缺陷有三个调用点时，单里要写「抽成一处共用函数＋调用点复用」，而不是「在 X 处补一段」——否则第四次收口还要再来一遍。
- **拿仓库里的历史产物当"统计对照基准"，判据必须同时规定它不许被自家测试改写**（C-16 R-C16-3）：
  我写「那 34 份是改前历史留档、没有这个键」——执行方照我的判据 d 在测试里调 `demo_main()`，**它自己就把其中 3 份重写成了改后产物**，于是"跑过一次 pytest 之后 34 份都缺键"这句话当场失效（实测剩 31 份）。
  两条都要写进单：① 对照基准要么落 `tmp_path`、要么只断言未被改写的子集，**不许一边改写一边拿它当历史**；
  ② 「样本里每一条 X 都满足 Y」这种判据，**必须另附一条 `count(X) ≥ 1`**——实测离线演示两案 `insufficient=0`，那句"全部有成因"是在空表上遍历、跑绿也不构成覆盖。
- **判据里的期望读数必须自带"怎么造出它"（夹具构造）**（2026-10-17 C-14b 复放前发现的，还是我的错）：

## 6. 仓库三道纪律（每次改动默认适用）

1. **零 LLM 优先**：能用确定性代码／机械闸解决的，不加模型调用；新闸与 skill 成对出现（没闸的 skill 是许愿）。
2. **丢件必须可见**：任何 `return`／`continue`／截断造成的材料丢弃，都要有披露出口；
   **披露≠召回**，写口径时两句都要在。
3. **测试期禁真调用**：新测试必须打桩；`tests/conftest.py` 有守卫，忘打桩当场炸。key 不进仓库、不进 U 盘明文。

## 7. 提交规矩（架构师执行）

- **一工单一 commit**（代码＋测试），标题带单号：`fix(scope): …（工单 C-x）`。
- **收口四项之外还有第五件＝对外材料里那三行数**（2026-10-20 C-14c 收口补）：`docs/proposal-formal.md` §5 的
  「app 行数／tests 行数／整套用例数」每落地一笔代码就会过期，而它是**官方交付物**、评委直接读。收口时顺手重跑
  `find app -name '*.py' | xargs wc -l`、`find tests -name '*.py' | xargs wc -l`、`pytest tests -q --collect-only`，
  连同「攻击面 59 条」那张分文件计数一起核（本轮实测 20/15/9/7/4/4 未变）；架构图「已知滞后」栏里那句 415 项／13,700 行已清，
  别再让它长回来。
- **文档另起一笔**：`docs(交接+方案): …`，同一笔里同步 HANDOFF 状态行与本文件提到的图。
- commit message 讲「为什么」并带实测数字；**不 push、不 `--no-verify`、不 amend 已提交内容**。
- **合 main 的节奏**：一条工作分支**攒到 3 张以上收口单、或距上次合并满 3 天**就该合一次，别把七天的量堆成一次"很久没 review"的大合并
  （2026-10-19 那次＝`main` 停在 10-12，中间 **85 commits／103 files** 从没进过 main，其中含判定口径变更，main 读者看不到）。
  合并方式＝**fast-forward**（`git merge-base --is-ancestor main HEAD` 为真时 `git merge --ff-only`），**只在本地合，仍然不 push**。
- **节律数的是「收口单张数」，不是 commit 笔数**（2026-10-20 C-14c 收口轮我自己写错过）：一张收口单会产生 2～4 笔 commit（代码＋文档＋复验），
  所以 `git rev-list --count main..HEAD` 只能用来**界定合并范围**（要 review 哪些文件），不能当"攒到几张"的计数器；
  合并后计数器清零，队列里记「距上次 FF 已收口 N 张」。**流水账数字（笔数／行数）不要写进排期句**——每次新增一笔文档它就过期，
  当场要用的时候现量。
- **整批 review 固定查三项**（缺一就是没做完）：① **两格环境在干净 `git clone` 上复放**（装／不装可选依赖各一格，加连跑 3 次看 flake）＋部署文档的第 3／第 5 步也真跑一遍；
  ② **引用体检**＝把所有开放单正文与队列行的 `file:line` 逐条开文件核对（本次 73 条，只漂 1 条；漂移会直接把执行方指错地方）；
  ③ **卫生**＝密钥／未入库产物（`out*/`、`.corpus`、`.fetched`、`cases/user-*/` 在 `git ls-files` 里必须 0 条）／官方样例集字节／本批新增二进制。
  review 改掉的每处口径都要落 commit 并进 HANDOFF 顶部编号项（本次＝⑮）。
- `CLAUDE.md` 是指向 `AGENTS.md` 的符号链接（同一份内容），改 `AGENTS.md` 即同步，不必也不许复制出第二份。

**§9.1 出单即附提示词（架构师义务，2026-10-16 加）**：只要有新单或单子改口径，架构师**必须同一条回复里**

# 海量材料 × 多用户并发 — 修正方案（答辩口径）

> 用途：被问到「一万/十万份材料怎么办」「几百人同时用会不会炸」时的标准答法与落地分期。  
> 原则不变：模型主张、程序复算；丢弃必披露；确定性优先；人是最高权限但动作入链。

---

## 0. 一句话总答

| 问题 | 当场答法 |
|---|---|
| 海量材料 | **今天**是单案卷研判引擎（切段 + BM25 装箱 + 证据闸）；**演进**是「索引库 → 议题检索 Top-K → 小段定位 + 父节扩窗 → 原管线」——不把十万份一次塞进提示词。 |
| 数百人并发 | **今天**是本机单用户演示台；**演进**是「任务队列 + 租户/会话隔离 + 网关配额」——研判异步化，禁止多人同写一份 `report.json`。 |

两块都不是「把切片再调细」能解决的，要补的是**检索生命周期**和**服务化边界**。

## 1. 问题 A：材料一万～十万份、又长又复杂

### 1.1 现状能力（诚实边界）

已具备、可继续用的：

- 层次切段（空行 / `一、` / `第X章` / Markdown）→ 引用颗粒度
- 案卷内 BM25 + 字符预算装箱 + 未入箱全披露
- 引文 / 数字 / 对撞等零 LLM 机械闸

明确不具备：

- 跨案卷持久索引与增量入库
- 语义检索 / 重排（默认链）
- 命中小段后自动扩父节（证据链版 small-to-big）
- 近重 / 对撞在万级信源上的可承受复杂度

### 1.2 目标架构（三层，不推翻现管线）

```
[材料库] 增量摄取 → 切段 → 写索引（段级 + 信源级元数据）
    ↓ 议题来了
[检索层] 过滤（主体/时间/类型）→ Top-K 信源 → Top-N 段（小块命中）
    ↓
[扩窗层] 命中段 → 同节父块 / 邻段（预算内）→ 拼「本议题案卷」
    ↓
[研判层] 闸与 panel 不变；入口是 hydrate 之后的本议题小案卷
```

要点：**十万份是库的问题；一次研判仍是「几十份信源 / 预算内段落」的问题。**

### 1.3 证据链版 small-to-big（建议做，名称可对外说「小段定位 · 父节扩窗」）

| 层级 | 单位 | 职责 |
|---|---|---|
| Small | 当前 segment（~500 字，层次节内） | 检索命中、引文锚定、机械核对 |
| Big | 同一结构标题下的父节（`一、…` 整节）或信源摘要 | 给分析师完整语境，减少半截条款 |
| 约束 | 扩窗计入 `material_char_budget`；扩入内容进披露账本 | 绝不静默多读 |

不做：滑动窗口重叠块（破坏 `segment_id` 唯一性与引文闸）。  
不做：摄取阶段 LLM 语义切分进默认链（贵、不可复现）。

### 1.4 分期修正（材料规模）

**P0 — 单案卷护栏 + 叙事（不假装已有跨库检索；跨库见 §5.1 刀1）**

1. **单案卷硬顶 + 披露**：单次研判信源/段数上限；超限拒绝或截断并披露（**无索引阶段不承诺「去库里检索」**）。
2. **父节扩窗（限额）**：命中段后预算内扩同节（封顶见 §6 M7）；单测锁定确定性。
3. **检索探针与槽位**（已有方向）：议题缺期间/主体早停；数字段优先钉箱。

**P1 — 可接「千级公告库」评测（与现有 ~2000 份披露文件对齐）**

1. **段级倒排索引落盘**（先 BM25/关键词，纯本地或可插拔 ES）：`segment_id → 信源 → 路径`；摄取增量更新。
2. **两阶段选料**：库检索 Top-K 信源 → 再对候选做现有 `pack_material`。
3. **近重 / 对撞降维**：先按主体+时间桶分片，再桶内配对；避免全局 O(n²)。
4. **可选语义重排**：网关 embedding 探测通过才启用；失败回退 BM25（与现「可插拔」一致）。

**P2 — 万～十万级生产库**

1. 对象存储 + 元数据库 + 索引集群；摄取与研判服务拆分。
2. 异步摄取流水线（OCR/PDF 版式与研判解耦）。
3. 冷热分层：热点段缓存；历史公告按需拉正文。

### 1.5 被追问时的对比表（材料）

| 错误期待 | 我们的修正 |
|---|---|
| 一次把十万份塞进模型 | 库检索 → 本次案卷 → 预算装箱 |
| 只靠切更碎 | 切段服务引用；规模靠索引与选料 |
| 经典 RAG 滑动窗口 | 小段引用 + 父节扩窗，块不重叠 |
| 上了向量就万事大吉 | 向量是重排插件；主链保持可复现 |

## 2. 问题 B：数百人同时使用

### 2.1 现状能力（诚实边界）

- 工作台默认 `127.0.0.1`，单用户本机演示
- `/api/run` 同步跑完才返回；产物直接写 `cases/*/out*/report.json`
- 无账号体系；人工改相关性/结论无多租户权限
- LLM 限流默认关；进程内全局预算/取消信号

**结论：演示与答辩够用；按 SaaS 数百并发会炸。**

### 2.2 目标架构（服务化最小集）

```
客户端 → API 网关（鉴权 / 限流）
          ↓
     研判任务队列（每任务独立工作目录 + run_id）
          ↓
     Worker 池（并发度 = f(CPU, 网关配额)）
          ↓
     对象存储：report / chain / progress（按 tenant/user/run 隔离）
          ↓
     只读工作台 ← 订阅 progress，禁止直写他人 run
```

### 2.3 分期修正（并发）

**P0 — 内网小团队（约 ≤20 人错峰，防「写坏文件」）**

1. **研判异步化**：`POST /api/run` → 立刻返回 `run_id`；进度读 `progress.json`（已有进度雏形可升格为任务态）。
2. **写路径锁**：锁的是 run 产物目录与 out 指针，不是整库；同库多议题检索可并行（§6 C1）。
3. **产物按 run 分目录**：`history/<run_id>/`，避免互相覆盖「当前 out」。
4. **进程级网关限流打开**：`llm_rate_limit_*` 按供应商令牌桶；超限排队而非打爆 key。
5. **操作者字段强制**：人工事件必须带 `operator`（模型层已预留，产品强制非空）。

**P1 — 部门级（约数十～百人，多数只读、少数在跑）**

1. **账号 + 角色**：查看 / 研判 / 仲裁改结论 / 管理；`relevance_override` 与密级走 clearance。
2. **多 Worker + 队列**（Redis/RQ/Celery 等择一）；水平扩展研判，工作台无状态化。
3. **租户或项目隔离**：资料库与 run 产物按 `project_id` 分桶。
4. **读多写少**：报告 CDN/本地缓存；写路径仅 Worker。

**P2 — 数百人同时在线（含多人同时点研判）**

1. 网关侧配额编排（按租户 QPS / 日预算）；排队与「预计等待」产品化。
2. 会话级取消与公平调度（防一人占满 Worker）。
3. 审计与合规：全量操作入链或平行审计日志；PII 与密级强制。
4. 不在单机 uvicorn 上承诺该档位。

### 2.4 并发档位口径（避免被「数百」一刀切）

| 档位 | 含义 | 我们承诺 |
|---|---|---|
| L0 本机演示 | 1 人 | **当前默认** |
| L1 小组 | ≤20 错峰，同时研判 ≤3 | P0 完成后可承诺 |
| L2 部门 | 百人级在线，同时研判数十 | P1 |
| L3 平台 | 数百同时研判 | P2 + 专门容量规划 |

答辩时先反问口径：是「数百人打开页面」还是「数百人同时点研判」——差一个数量级。

### 2.5 被追问时的对比表（并发）

| 风险 | 修正 |
|---|---|
| 同文件覆盖 | run 级目录 + 案卷写锁 |
| 同步请求拖死服务 | 异步任务 + Worker 池 |
| API 被打爆 | 租户/全局令牌桶 + 队列 |
| 越权改结论 | 账号角色 + clearance |
| 全局变量互踩 | 预算/取消信号改为 per-run 上下文 |

## 3. 两条线的依赖关系（别拆错序）

```
刀1 索引 → 刀2 两阶段选料 → 每次都是小案卷 → 并发扩容才有意义
刀3（近重/扩窗）配套刀2；扩窗不是规模主前置
并发：写路径锁 + per-run 隔离（库只读可并行，勿锁死整库）
```

- 只做并发、不做选料：每人仍可能点「全库开跑」→ Worker 与网关照样炸。  
- 只做索引、不做隔离：多人同写 out → 链与报告损坏。  
- **正确叙事**：规模上「先选后判」；并发上「先隔后跑」。细节漏洞见 §6。

## 4. 与现有交件表述的衔接（可直接贴进方案/口述）

- 方案已写：六至十份为当前案例规模；BM25 装箱服务超大输入；更大规模语义检索与按需取段列入演进；多人协同在数据模型预留。  
- 本修正方案把演进拆成 **可验收的 P0/P1/P2**，并补上并发档位，避免被听成「以后再说」。  
- 现场演示继续打 L0/L1 能力（证据链、闸、链、工作台）；被问规模/并发时亮本页架构图与分期，不承诺未做的 L3。

## 5. 两套「下一刀」——别混

先前写的「父节扩窗 / run 隔离 / N÷M 披露」是**答辩叙事 + 并发防写坏**，
**几乎修不动「一万～十万份」的根因**。材料规模要另开三刀，缺陷一一对应：

### 5.1 一万～十万份：缺陷 → 修复刀（材料专属）

| # | 缺陷（会炸/会瞎） | 修复刀 | 验收判据 |
|---|---|---|---|
| **刀1** | 无持久索引；每次 `load_case` 扫目录切段进内存 | **段级索引 + 元数据契约 + 切段版本/墓碑** | 增量更新一份不重切全家；切段版本不符则拒绝沿用旧索引。验收按 **10 万段** 量级，不把「1 万段」当成「1 万份」 |
| **刀2** | 8 万字装箱面对「海」；轮转公平稀释相关源 | **两阶段选料 + 类型保底 + 实体强制入候选 + hydrate** | 本次信源硬顶（如 ≤50）；官方/报告类有保底席；漏召回必须披露。三刀打通的是千～万份路径 |
| **刀3** | 近重/对撞偏 O(n²)；细切后段爆炸、跨段语境丢 | **LSH 近似近重（无主体时）+ 限额父节扩窗** | 扩窗 ≤ 预算 30%，且先钉命中段；无标题的前言不扩窗 |

三刀是**必要非充分**：做完才有规模修复路径，**不等于十万份已经能跑**。十万份还要外存倒排、P2 存储/集群，以及金标 Recall@K。父节扩窗单独做只能改善长文语境。

### 5.2 答辩/现场另一套三刀（并发 + 叙事，不替代 5.1）

1. **单次纳入数披露**（库内 N / 本次 M）— 配合刀2的产品口径  
2. **run 级目录 + 写路径锁 + 异步** — 修的是「数百人」，不是「十万份」  
3. **父节扩窗** — 并入材料刀3，不再当规模主修复单独吹

### 5.3 答辩怎么讲才不被追问翻车

- 问「十万份缺陷怎么修」→ 答 **5.1 三刀**（索引 → 两阶段选料 → LSH/扩窗），并主动补一句：**三刀打通千～万份，十万份还要外存索引与召回评测**；今天演示仍是单案卷。  
- 问「切片是不是就解决了」→ **不是**；切片只服务引用颗粒度，规模靠刀1+刀2。  
- 问「small-to-big」→ 落在刀3 扩窗，且依赖刀2 先把候选集收小。

## 6. 方案复查：漏洞与补丁（内部审，答辩被追也按此答）

### 6.1 材料线 — 高危漏洞

| ID | 漏洞 | 为何会翻车 | 补丁（方案必须补上的约束） |
|---|---|---|---|
| M1 | **P0「超限只检索」与无索引矛盾** | §1.4 P0-1 写「超限只检索不入箱」，但刀1 索引在 P1——今天没有库检索 | P0 口径改为：**无索引前不做跨库检索承诺**；P0 只做「单案卷内硬顶 + 披露」。跨库选料从刀1落地日起生效 |
| M2 | **验收「1 万段」≠「1 万～10 万份」** | 一份长 PDF 可切出数百段；1 万份 ≈ 百万段级。用 1 万段验收会自我安慰 | 刀1 验收改为：**10 万段**冷查 Top-100 延迟档 + **1 万份元数据**过滤；并单列「全库首建索引耗时/失败率」 |
| M3 | **Top-K 召回失败 = 静默盲区** | 正解不在候选集时，闸只能保证「不编造」，不能保证「不漏判」；谣言翻印可能挤掉唯一官方通告 | 刀2 强制：**信源类型配额**（如 official/report 保底席位）+ **议题实体强制入候选**；报告披露未入选原因；用金标集测 Recall@K |
| M4 | **过滤依赖元数据，元数据未设计** | 架构图写「按主体/时间/类型过滤」，当前大量材料无可靠时间/主体 | 刀1 同期交付：**信源级元数据契约**（路径哈希、标题、类型、时间可空+披露、主体可空+披露）；缺字段进未标注桶 |
| M5 | **增量索引与切段策略变更** | 层次切片一改，旧 segment_id 与旧报告引文错位；文件更新/删除无墓碑 | 索引带 **切段版本号**；变更废旧段 ID、写墓碑；旧 run 只保证历史自洽 |
| M6 | **「pipeline 不变」不严谨** | 选料后仍须 hydrate 段正文；对撞/近重跑在案卷上 | 刀2 输出：**候选 segment_id → 读正文组装 Dossier**；闸只看见本议题案卷 |
| M7 | **父节扩窗挤占预算** | 扩窗吃掉预算，挤掉其他高相关信源 | 扩窗配额封顶（如预算 30%）；先钉命中段与类型保底，再扩窗 |
| M8 | **分桶近重依赖主体抽取** | 主体切错则漏同源谣言；桶太大仍 O(n²) | 无主体时用 **LSH/minhash 近似近重**；有主体再精配。分桶是优化不是完备 |
| M9 | **确定性 vs 集群索引** | 「同输入同输出」与 ES/ANN 漂移冲突 | **闸与评分确定性不变**；检索在「同一索引快照+算法版本」下可复算；ANN 不声称逐字节可复现 |
| M10 | **索引安全与多租户泄露** | 缓存投毒放大到全库；租户互读 | 索引挂 project_id；内容哈希校验；检索强制租户过滤（与并发 P1 绑定） |

### 6.2 并发线 — 高危漏洞

| ID | 漏洞 | 为何会翻车 | 补丁 |
|---|---|---|---|
| C1 | **单案互斥锁粒度过粗** | 同库多议题并行是常态 | 锁 **run 写路径 / out 指针**，库检索只读可并行 |
| C2 | **队列≠成本可承受** | 数百人×多分析师先烧穿 API | 租户日预算、同题短 TTL 缓存、可降级编队 |
| C3 | **异步后全局预算/取消互踩** | 现有偏进程内 | per-run 上下文升为 P0 硬依赖 |
| C4 | **只读也可能拖死** | 大 report + 轮询 | progress 轻量；图谱只对当前 run |

### 6.3 结构自洽

| ID | 问题 | 处理 |
|---|---|---|
| D1 | §1.4 P0 与 §5.1 刀序矛盾 | 以 §5.1 为材料修复真源；P0 不做跨库检索承诺（M1） |
| D2 | §3 把父节扩窗当材料主前置 | 改为刀1→刀2 为并发前置；扩窗属刀3 |
| D3 | 三刀夸大到十万份 | **三刀必要非充分**：先打通千～万份；十万份还要 P2 存储/集群 + 召回评测 |

### 6.4 修正后依赖

```
刀1 索引+元数据+版本 → 刀2 两阶段选料(+类型配额/实体保底/hydrate)
                         → 刀3 LSH或分桶近重 + 限额父节扩窗
                         → 小案卷 → 现有 pipeline
并发：per-run 上下文 + 写路径锁 + 队列 + 租户配额/缓存/降级
```

### 6.5 复查结论

- 方向对，但原稿混了「能讲」与「能修」；刀1 验收偏小、漏召回/元数据/hydrate 未写清。
- **补上 M1–M10、C1–C4 前，不宜拍胸脯「三刀做完=十万份」。** 稳口径：三刀打通千～万份路径；十万份还要 P2 + Recall 评测。
- 被追问优先主动甩 **M3（漏召回）** 和 **M2（份≠段）**。

## 7. 已开工（第一刀，默认关闭）
